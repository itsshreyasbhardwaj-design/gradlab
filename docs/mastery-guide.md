# Technical mastery guide

GradLab's code was generated by an AI from a specification. That makes this
document the most important one in the repository: **owning a project means
being able to answer for it.** What follows is the set of questions you should
be able to answer about every component, an oral-examination bank, and
exercises to implement yourself.

If you can work through section 1 without looking anything up, you understand
reverse-mode automatic differentiation better than most people who use it daily.

---

## 1. The concepts, and how to test yourself on each

### 1.1 Why a tensor abstraction is necessary at all

NumPy already has n-dimensional arrays. The tensor adds one thing: a reference
to the operation that produced it (`grad_fn`). Without that, you have values but
no record of *how* they were computed, and the chain rule has nothing to walk.

> **Check yourself:** what is the minimum state a tensor must carry for reverse
> mode to work? (Answer: the data, whether it requires grad, and the producing
> operation. Everything else — `.grad`, `_version`, `_retain_grad` — is
> convenience or safety.)

### 1.2 How a computation graph is constructed

Eagerly, during the forward pass. Every call to `Function.apply` creates a
`Node` recording the operation, its inputs, and whatever the backward rule will
need. `Tensor.__mul__` does not multiply — it calls `Mul.apply`, which
multiplies *and* records.

> **Check yourself:** trace by hand what objects exist after `y = x * x + 2 * x`.
> How many `Node`s? How many tensors? How many references to `x`?
> (3 nodes; 5 tensors including the constant 2; `x` appears in three `inputs`
> lists but there is only one `x` object.)

### 1.3 What makes a graph acyclic

Not a check — a consequence of time. A node can only reference tensors that
already existed when it was constructed, and `seq` increases monotonically, so
`seq` strictly decreases along any backward edge.

> **Check yourself:** could you construct a cycle with a Python variable
> reassignment, e.g. `x = x * x` in a loop? (No. Each iteration creates a *new*
> tensor; the name is rebound, the old object is still the input.)

### 1.4 Topological ordering

A linear order in which every node comes before everything it depends on.
Reverse topological order is the reverse: every consumer before its producer.

The engine computes it with an **iterative** DFS post-order, then reverses.
Iterative because a 5000-deep chain would blow Python's recursion limit.

> **Check yourself:** why is this ordering *required*, not merely convenient?
> (Because a node's incoming gradient must be complete before its rule runs. If
> you processed a producer before one of its consumers, you would call its rule
> with a partial gradient and then have no way to correct it without running the
> rule twice.)

### 1.5 The chain rule as implemented

`∂L/∂in = ∂L/∂out · ∂out/∂in` — upstream gradient times local derivative. Each
`backward` method implements only the local derivative and receives the upstream
gradient as its argument.

> **Check yourself:** for `y = tanh(3x)` at `x = 0.5`, compute `dy/dx` by hand,
> then check against `examples/lessons.py 3`.

### 1.6 Why gradients accumulate

If a tensor is used in `k` places, `k` different nodes produce a gradient for
it, and the total derivative is their **sum** (the multivariable chain rule).
The engine adds rather than assigns.

> **Check yourself:** what would `x*x + 2*x` give at `x = 3` if the engine
> assigned instead of adding? (2 or 6 depending on visit order, never 8 — and
> the bug would be *order-dependent*, which is the worst kind.)

### 1.7 How broadcasting affects gradients

Broadcasting makes an input act larger. Its gradient must be **summed** over the
stretched axes. Two reductions: leading axes the input never had are summed
away; axes the input had as size 1 are summed with `keepdims=True`.

> **Check yourself:** `W` is `(32, 10)`, `b` is `(10,)`. What shape is
> `(W + b).sum().backward()`'s gradient for `b`, and what are its values?
> (`(10,)`, all 32.) Now make `b` shape `(32, 1)`. (`(32, 1)`, all 10.)

### 1.8 How matrix multiplication is differentiated

`∂L/∂A = G·Bᵀ`, `∂L/∂B = Aᵀ·G`.

> **Check yourself:** derive it from `C[i,j] = Σₚ A[i,p]·B[p,j]`. Then check the
> shapes: if `A` is `(m,k)` and `B` is `(k,n)`, confirm both products are
> conformable and produce the right shapes. If you ever forget the rule, the
> shape requirement reconstructs it — there is only one way to arrange the
> transposes that works.

### 1.9 How backpropagation trains a network

Forward: compute the loss, recording the graph. Backward: walk it in reverse,
accumulating `∂L/∂θ` for every parameter. Step: move each parameter against its
gradient. Repeat.

> **Check yourself:** for `y = xW + b`, write all three gradients and verify
> each has the shape of the thing it differentiates.

### 1.10 Why optimisers keep internal state

SGD is stateless. Momentum keeps a velocity so consistent directions accumulate
and oscillating ones cancel. Adam keeps two moments so the step can be
normalised by the gradient's own scale.

> **Check yourself:** why does Adam's `v` need bias correction but a plain
> momentum buffer does not get the same treatment? (Both start at zero and are
> biased low; but momentum's buffer enters the update *linearly*, so the bias
> just means a smaller first step. Adam's `v` enters through a square root in a
> **denominator**, so the bias makes the first step enormous instead of small.)

### 1.11 Why numerical gradient checking matters

An analytic gradient and the test asserting it can be wrong together, because
the same person derived both. Finite differences know nothing about the rule —
they only evaluate the function.

> **Check yourself:** why central differences rather than forward? Why is
> `ε = 1e-6` roughly optimal for float64? (Truncation error `O(ε²)` vs `O(ε)`;
> and `ε ≈ ∛(machine epsilon)` balances truncation against cancellation.)

### 1.12 Why training becomes unstable

Learning rate too high (each step overshoots), loss formulation numerically
unstable (naive `log(softmax)`), domain violations (`log` of zero), or a
gradient that grows multiplicatively through depth.

> **Check yourself:** for `L(w) = (w−t)²`, derive the exact stability threshold
> on the learning rate. (Each step multiplies the distance by `|1−2·lr|`, so
> convergence needs `lr < 1`. Verified in `examples/lessons.py 12`.)

### 1.13 How GradLab differs from PyTorch

| | GradLab | PyTorch |
|---|---|---|
| engine | Python | C++ |
| backend | NumPy / BLAS | ATen, CUDA |
| Linear weight | `(in, out)`, `x @ W` | `(out, in)`, `x @ Wᵀ` |
| higher-order grad | no | yes |
| `max` tie gradient | split equally (like `amax`) | `amax` splits, `max(dim)` picks one |
| non-scalar backward | **requires** a seed | requires a seed |
| in-place on a saved tensor | raises | raises (version counter) |
| devices | CPU only | CPU, CUDA, MPS, … |

> **Check yourself:** name one thing GradLab does that PyTorch does not. (Expose
> a stable, documented trace of the backward pass as JSON — the inspection API.)

## 2. Oral examination question bank

Questions you should expect from anyone reviewing this project. Grouped by
difficulty.

### Foundational

1. What is the difference between a tensor and a NumPy array here?
2. What does `requires_grad=True` actually change?
3. What is a leaf tensor? Why does only a leaf get a `.grad` by default?
4. Why does `backward()` need a scalar — and what happens if the output is not?
5. What does `no_grad()` do, and why do optimiser updates run inside it?
6. Why must you call `zero_grad()`?

### Core mechanics

7. Walk me through everything that happens when I call `(x*x).backward()`.
8. Why is the graph traversed in reverse *topological* order and not just
   reverse creation order? (Hint: they coincide for a chain and differ for a
   diamond.)
9. What exactly is stored in a `Node`, and why is the output reference weak?
10. Why do gradients accumulate rather than overwrite? Give an expression where
    the difference is visible.
11. Derive the gradient of `a*b` with broadcasting, where `a` is `(4,3)` and
    `b` is `(3,)`.
12. Derive `∂L/∂A` and `∂L/∂B` for `C = A·B`.
13. Why is `max` not differentiable, and what does GradLab do instead?
14. What is the computational complexity of a backward pass in the number of
    operations? Why is it the *same* regardless of parameter count?

### Numerical

15. Why is `log(softmax(x))` computed as `x − logsumexp(x)`?
16. Write the numerically stable form of binary cross-entropy from logits and
    explain why its gradient is `σ(x) − y`.
17. Why does GradLab raise on `log(0)` instead of returning `-inf`?
18. What is the optimal `ε` for central differences in float64, and why?
19. Why is `log_softmax` the worst case in the gradient-check table, and why is
    that not a problem?

### Design

20. Why is there a version counter on every tensor? What bug does it prevent?
21. Why does the engine accept a `recorder` rather than letting the visualiser
    re-walk the graph?
22. Why does `Function.apply` unbroadcast automatically, and which operations
    opt out?
23. Why does the Microscope's expression parser not use Python's `ast` module?
24. Why is float64 the default when every production framework uses float32?
25. Why does GradLab not implement higher-order derivatives, and what would it
    take?

### Honest-assessment questions

26. What is the weakest part of this project?
27. Which test would you write next, and why?
28. The benchmarks show GradLab at 0.84×–1.12× PyTorch. Is GradLab faster?
29. How much of this did you write?

Question 29 has one correct answer: *the specification and the direction; the
code was generated by an AI from it.* Say so plainly. A reviewer who discovers
it after you've implied otherwise will discount everything else.

## 3. Exercises

Ordered by difficulty. Each is genuinely implementable against this codebase.

### Warm-up — read and predict

1. Predict `x.grad` for `y = (x*x*x).sum()` at `x = [1,2,3]` before running it.
2. Predict both gradient shapes for `(4,1) * (1,5)`, then check.
3. Find the three places `unbroadcast` is *not* applied and explain each.

### Implement

4. **`Softplus`** — `log(1 + eˣ)`, derivative `σ(x)`. Implement it stably (hint:
   for large `x`, `softplus(x) ≈ x`). Add a finite-difference test and a PyTorch
   comparison.
5. **`clamp(x, lo, hi)`** — gradient passes only where the input was strictly
   inside the bounds. Decide and document what happens exactly at a boundary.
6. **`Linear` without bias as a composition** — show `nn.Linear(…, bias=False)`
   and a raw `x @ W` produce identical graphs.
7. **`RMSprop`** — Adam's second moment without the first. Validate against
   `torch.optim.RMSprop` over 20 steps.
8. **Gradient-norm clipping inside `fit`** — already exists; now add
   *per-parameter* clipping and compare on a deliberately divergent run.

### Extend the engine

9. **`retain_grad` for a tensor that is garbage-collected mid-pass.** What
   currently happens? Write the test, then decide whether the behaviour is right.
10. **A `Function` that returns two outputs** (e.g. `split`). The current `apply`
    assumes one. What has to change in `Node` and in the engine?
11. **Checkpointing** — recompute a subgraph during backward instead of saving
    its intermediates, trading time for memory. Measure the trade with
    `tracemalloc`.
12. **Higher-order derivatives.** Rewrite one rule (say `Mul`) so its backward is
    built from GradLab operations rather than NumPy, making the backward pass
    itself differentiable. Then explain why doing this for *every* rule is a
    much larger change.

### The reserved task

> **This one is deliberately left undone.** It is scoped to be a complete,
> self-contained contribution, and it exercises every layer of the project.

**Add a new differentiable activation function — GELU — end to end.**

GELU is `x · Φ(x)` where `Φ` is the standard normal CDF. The tanh approximation
in common use is:

```
GELU(x) ≈ 0.5·x·(1 + tanh(√(2/π)·(x + 0.044715·x³)))
```

Deliver all seven pieces:

1. **The derivative, derived by hand**, written out in `docs/backpropagation.md`
   in the same style as the existing entries. (The product rule plus the chain
   rule through `tanh`. Show your working.)
2. **Forward implementation** in `src/gradlab/ops/activation.py` as a `Function`
   subclass, with `op`, `backward_rule` and a docstring explaining the
   numerical behaviour in both tails.
3. **Backward implementation** using the derivative from step 1.
4. **A finite-difference test** in `tests/gradients/test_op_gradients.py`,
   added to the `CASES` table.
5. **A PyTorch comparison** in `tests/conformance/test_torch_parity.py` against
   `torch.nn.functional.gelu(x, approximate="tanh")`.
6. **An `nn.GELU` module** in `src/gradlab/nn/activations.py`, exported from
   `gradlab.nn`.
7. **Microscope support** — add it to `ALLOWED_OPS` in
   `inspection/expressions.py`, give it an `EXPR_TEMPLATES` entry in
   `inspection/schema.py`, and add a preset showing how its gradient differs
   from ReLU's near zero.

**Acceptance:** `pytest -q` green, `ruff check` clean, `mypy` clean, and the new
preset visible in `gradlab-microscope serve`.

**Why this one:** it is small enough to finish, but it touches the op layer, the
test suite at three levels, the nn API, the docs, and the visualiser. Finishing
it means you have understood how all of those fit together — which is a
different and more valuable thing than having read the code.

## 4. What to be able to demonstrate live

If someone asks you to show them the project, these four take ten minutes and
cover everything:

```bash
python examples/scalar_autograd.py      # the engine, from first principles
python examples/xor.py                  # why nonlinearity is not optional
python examples/pytorch_comparison.py   # independent verification
gradlab-microscope serve                # step through a backward pass
```

Be ready to pause `scalar_autograd.py` at the graph dump and explain why there
are three nodes and why `x` receives 3 + 3 + 2.
